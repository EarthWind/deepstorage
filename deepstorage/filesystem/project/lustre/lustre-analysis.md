# Lustre 调研（五）：设计评估与对 LightStore 的启示

> 基线：lustre-release commit `eadb94b`

Lustre 与 LightStore 的架构不可直接对照——内核态、无原生副本、公式化布局、
面向少量超大文件——这些前提都不同。它的价值在于：**它是唯一一个真正解决了
"分布式文件系统的强一致语义"的开源系统**，而这些机制是 JuiceFS 和 CubeFS
选择绕开的。绕开是对的还是不对的，要看过 Lustre 付了什么代价才能判断。

## 1. 三条路线的定位

```
                强一致 ────────────────────────────► 弱一致
                   │                                    │
                Lustre                        CubeFS  JuiceFS
                   │                                    │
             锁 + 回调                            TTL + 重新验证
             服务端有状态                          服务端无状态
             客户端失联 → 驱逐                     客户端失联 → 自愈
             语义完整                              语义有缺口
             运维复杂                              运维简单
```

**LightStore 目前的位置更接近 CubeFS**（元数据强一致、数据 close-to-open 级别），
这对于"超大规模 + 高吞吐"的目标是正确的默认选择。
但下面几个点值得考虑是否局部引入 Lustre 的机制。

## 2. 可借鉴的设计

### 2.1 公式化索引：当写入是纯顺序时，元数据可以是 O(1) ★★

Lustre 的条带布局是**公式**不是**列表**：给定文件偏移，
`(offset / stripe_size) % stripe_count` 直接算出在哪个对象。
一个 100 TB 的文件，layout EA 大小与一个 1 MB 的文件完全相同。

LightStore 的 extent 索引是逐条 `(inode_id, file_offset) → Loc`。
对于**纯顺序写的大文件**，这些 Loc 高度规律：同一个卷内连续偏移、等长 record。

结合 [CubeFS 调研](../cubefs/cubefs-blobstore.md) §5 提到的游程压缩，
可以更进一步：

```
普通 extent:  (inode, file_offset) → Loc{volume_id, offset, length, cookie}
游程 extent:  (inode, file_offset_start) →
              RunLoc{volume_id, offset_start, record_size, record_count, cookie_base}
```

一次 64 MiB 攒批提交若产生 16 条 4 MiB 的连续 record，可以压成一条。
**对顺序写大文件，元数据条数降一个数量级以上。**

前提是 record 在卷内连续分配——这需要 SDK 在攒批时向同一个卷申请连续空间，
而不是每条 record 独立选卷。**建议把"批内连续分配"作为 SDK 写路径的优化目标。**

### 2.2 乐观粗粒度 + 竞争时自动细化 ★★★

Lustre 的 extent lock 扩张（[LDLM 文档](lustre-ldlm.md) §4）：
客户端请求 `[4096, 8192)`，无竞争时服务端授予 `[0, EOF]`；
冲突锁超过 32 个时收缩回按需大小。

**这个模式在 LightStore 有至少三处直接适用：**

1. **卷分配**：SDK 向 DataServer 申请写入空间时，无竞争则一次性拿到一大段
   卷内区间的独占写权，后续追加零 RPC；有多个 SDK 竞争同一卷时收缩为逐次申请。
   这能显著降低小文件写入的元数据往返。
2. **Range 租约**：MetaServer 的读租约可以按目录子树粒度授予，
   竞争时细化到单 inode。
3. **索引提交批次**：无竞争时攒更大的批（降低提交频率），
   检测到同文件有其他写者时立即缩小批次（降低冲突窗口）。

这条规律的价值在于**它让"默认配置"不再需要在性能和并发之间预先选边**——
系统自己按实际竞争情况调整。LightStore 目前很多参数（攒批 64 MiB）是静态的，
可以考虑改成竞争自适应。

### 2.3 用冲突作为"加强保证"的触发信号（COS 模式）★★★

Lustre 的 Commit-on-Sharing（[LDLM 文档](lustre-ldlm.md) §2）：
事务提交后把锁降级为 COS 模式，**只有当第二个客户端来碰同一对象时**
（即真的发生了共享），才强制把前面的事务同步落盘。

抽象出来的规律：

> 强保证的代价只在真正需要它的时候付。用冲突检测作为触发器，
> 而不是无条件地为所有操作都付代价。

**LightStore 的直接适用场景：**

- **索引提交的持久性**：SDK 攒批提交 extent 后，MetaServer 的 Raft 提交
  可以异步返回。只有当**另一个客户端来读这个 inode** 时，
  才强制等待该 inode 的索引真正 committed。单写者场景（绝大多数）零等待。
- **卷密封的同步点**：卷密封通常要等所有副本对齐。如果没有第二个读者，
  可以延迟对齐；有读者来了再强制同步。

这比"所有写入都同步"和"所有写入都异步"都好，且实现成本不高——
需要的只是一个"这个对象最近被谁碰过"的标记。

### 2.4 元数据锁/缓存必须按用途拆位，不能按 inode 粒度 ★★★

Lustre 的 inodebits（[LDLM 文档](lustre-ldlm.md) §5）把一个 inode 的锁拆成
LOOKUP / UPDATE / OPEN / LAYOUT / PERM / XATTR / DOM 七个独立位。

**核心洞察：inode 的不同属性变化频率相差几个数量级。**

| 类别 | 变化频率 | 缓存策略 |
|------|---------|---------|
| 数据位置索引（layout） | 极低 | 可长期缓存 |
| 权限、owner | 极低 | 可长期缓存 |
| 名字、父目录 | 低 | 可长期缓存 |
| size、mtime | **每次写都变** | 短周期或按需 |

如果按 inode 粒度失效，那么**任何一次写入都会让该文件的路径解析缓存、
权限缓存、布局缓存全部失效**——而这些东西根本没变。

LightStore 的 SDK 会缓存 inode 属性和 extent 索引。
**建议现在就把缓存条目按"变化频率"分组**，而不是等到性能问题暴露再改：

- `extent 索引 + 权限 + 名字` → 长 TTL / 长租约
- `size + mtime` → 短 TTL，或从写入方直接读

这个改动在设计早期几乎零成本，后期改则要动客户端协议。

### 2.5 Glimpse：读取"正在被写的文件"的精确元数据 ★★

Lustre 的 Glimpse AST（[LDLM 文档](lustre-ldlm.md) §3.3）：
`stat()` 一个正在被写的文件时，服务端向持锁的写者索取 LVB（size/mtime），
**写者不释放锁、不中断写入**，只汇报当前值。

LightStore 的等价缺口：SDK 攒批期间（最多 64 MiB 未提交），
其他客户端 `stat` 得到的文件长度是偏小的。

是否需要修补取决于目标场景：

- 训练 checkpoint、日志、数据管道等"边写边被监控"的场景 → 是真实问题
- 纯批处理（写完再读）→ 不是问题

**如果需要，最轻量的实现不是引入完整锁机制**，而是：
MetaServer 记录"该 inode 当前有哪个 SDK 在写"（写入时已有这个信息），
`stat` 请求转发给那个 SDK 索取当前长度，超时则回退到已提交长度。
这是 Glimpse 的精简版，不需要锁、不需要回调注册，只需要一条转发路径。

### 2.6 Grant：写缓冲的空间预留 ★★★

见 [恢复文档](lustre-recovery.md) §4。**这是本次调研中对 LightStore
最实际的一个发现。**

LightStore 的 SDK 攒批 64 MiB 后才提交。`write()` 返回成功时数据还在 SDK 内存里。
**如果落卷时集群满了，应用已经认为写成功了，此时无处报错。**

设计文档目前没有涉及这一点。必须显式做出选择：

| 方案 | 语义 | 复杂度 |
|------|------|--------|
| Grant 式额度预留 | 最强，`write()` 成功即保证有空间 | 高 |
| 写时向 DataServer 预留卷内区间 | 中等 | 中 |
| 文档化"仅 Sync/Close 保证持久" | 弱（同 JuiceFS/CubeFS） | 零 |

即使选第三种，**也要显式写进文档**，而不是留作未定义行为。

### 2.7 在线重分片的"水位分界"手法 ★★

Lustre 条带目录迁移用 `lmv_migrate_offset`（[布局文档](lustre-layout.md) §3.1）：
迁移中的目录，此偏移之前的条带已在新位置、之后的还在旧位置，
读路径按条目哈希落在水位前后决定去哪找。

**不停写、不双写、不锁整个目录**，只在元数据里记一个进度水位。

LightStore 的 Range 分裂/合并/迁移面临同样问题。这比"迁移期间把 Range 置为只读"
可用性好得多。建议在 Range 迁移设计里明确采用水位分界 + 读路径双向路由。

### 2.8 非幂等操作的去重槽位要按类别分开 ★

Lustre 的 `lsd_client_data` 为 `MDS_CLOSE` 单独保留了一组
`lcd_last_close_transno/xid/result/data`（`include/uapi/linux/lustre/lustre_disk.h:179`），
因为 close 会与其他操作乱序，单一"最后一次操作"记录不足以去重。

LightStore 的 MetaServer 需要防客户端超时重发导致的重复执行
（Raft 保证 apply 一次，但不防重复提交）。**去重表的键设计要考虑
不同操作类别可能并发**，不能只记"该 client 的最后一次操作"。

### 2.9 主动通知优于超时发现 ★★

Imperative Recovery（[恢复文档](lustre-recovery.md) §6）：
MGS 主动通知客户端 target 已重启，恢复窗口从数分钟缩到数秒。

LightStore 的 Manager 已在维护成员表与心跳。
**Range 主切换、卷密封、DataServer 下线都应走主动通知**，
而不是让 SDK 靠 RPC 超时去发现。这是低成本高收益的可用性改进。

## 3. 需规避的设计

### 3.1 锁模型的客户端驱逐耦合 ★★★

见 [LDLM 文档](lustre-ldlm.md) §6。这是 Lustre 最大的运维痛点：

服务端等待 BL AST 响应时是阻塞的。一个网络抖动的、内存吃紧的、
或者干脆挂掉的客户端，会让所有等待同一把锁的客户端一起卡住。
唯一解法是**驱逐**——被驱逐客户端的脏数据直接丢弃，IO 返回 EIO。

**"client eviction" 是 Lustre 生产集群最常见的告警。**

这就是为什么 JuiceFS 和 CubeFS 都选 TTL：**不是做不到强一致，
是不愿意让一个慢客户端拖垮全局。**

**LightStore 不应该引入需要"服务端阻塞等待客户端响应"的机制。**
上面 §2.2/§2.3/§2.5 建议的几处借鉴都刻意避开了这一点：

- 锁区间扩张 → 改为空间分配的租约，**租约到期自动失效，不需要回调**
- COS → 改为标记 + 读者触发，**读者主动查，不是写者被动回调**
- Glimpse → 转发查询 + **超时回退到已提交值**，不阻塞

**判断准则：任何机制，如果客户端不响应会导致其他客户端阻塞，就不要引入。**
可以让不响应的客户端自己受损（拿不到锁、数据被丢弃），
但不能让它影响别人。

### 3.2 公式化布局在容量不均衡下的脆弱性 ★★

Lustre 的条带布局在创建时就固定了用哪些 OST。OST 满了之后，
已有文件无法继续写入——即使集群整体还有大量空间。

Lustre 为此打了一系列补丁：OST pool、PFL、SEL（自扩展布局）、
空间感知的 OST 选择策略。**每一个都是在给"位置预先确定"这个决定还债。**

LightStore 的"写时选卷"天然回避了这个问题。
**不要为了减少元数据而引入位置预先确定的布局。**
§2.1 建议的游程压缩是安全的，因为它压缩的是**已经写完的**连续 record，
不是预先规划的位置。

### 3.3 FLR 不是真冗余 ★★

Lustre 的 FLR 是延迟同步的镜像：写入时只写主镜像，其余标记 STALE，
事后手动或后台重新同步（[布局文档](lustre-layout.md) §2.3）。
**写入期间实际只有一份数据。**

这是历史包袱——Lustre 的可靠性建立在"后端 RAID 不丢数据"之上。

LightStore 的卷级同步复制（副本三写 / EC 条带）是正确的选择，
不要被 FLR 的"轻量"迷惑。FLR 唯一值得借鉴的是
`LCME_FL_PREF_RD` / `LCME_FL_PREF_WR` 标志——**允许把不同副本标记为读/写优选**，
可用于分级存储（读走 SSD 副本、写走 HDD 副本）。

### 3.4 分片不自动分裂 ★★

Lustre 的条带目录必须用户显式创建（`lfs mkdir -c N`），
目录变大后需要管理员手动重条带。万亿文件规模下这不可接受。

LightStore 的"Range 自动分裂/合并/迁移"是必需的。
但 Lustre 不做自动化可能也有道理：**分裂通常在高负载时触发，
而分裂本身会进一步加剧负载**。

**建议给自动分裂加两道保护**：
- **滞回**：分裂阈值与合并阈值之间留足够间隔，避免抖动
- **限流**：全局同时进行的分裂数有上限，且在集群负载高时降速

### 3.5 深度分层带来的可读性成本 ★

一个元数据操作要穿过 `llite → lmv → mdc → ptlrpc → mdt → mdd → lod → osd → ldiskfs`
九层。这带来了后端可替换性（ldiskfs / ZFS / wbcfs），
但也让 Lustre 成为出了名的难以入门和调试的代码库。

LightStore 已经是三组件清晰划分，**不要为了"未来可能替换存储引擎"
提前引入过多抽象层**。存储引擎抽象一层足够。

## 4. 三份调研的横向结论

把 JuiceFS、CubeFS、Lustre 放在一起，有几条规律是三者共同验证的：

1. **反向指针是可扩展 GC 的前提**。Lustre 的 `filter_fid.ff_parent`、
   LightStore 的 `owner=(inode, file_offset)` 是同一设计；
   JuiceFS 没有，所以只能全量扫描，EiB 级不可行。
2. **版本/epoch fencing 是必需的**，三者都有：
   Lustre 的 `ff_layout_version`、CubeFS 的 `vuid.epoch`、LightStore 的 `vol_epoch`。
3. **分片数多时必须 quorum，分片数少时可以 write-all**。
   CubeFS 在同一项目里做了两个相反选择，Lustre 的 EC 组件同理。
4. **元数据的不同字段变化频率差几个数量级**，缓存/锁必须按此分组。
   Lustre 用 inodebits 显式解决；另两者没有，是已知的性能问题。
5. **主动通知优于超时发现**，Lustre 的 Imperative Recovery、
   CubeFS 的 Master 心跳推送路由表，都是这个思路。

一条**没有共识、需要 LightStore 自己决策**的：

> **`write()` 返回成功后、数据落盘前，集群满了怎么办？**
> Lustre 有 grant；JuiceFS 和 CubeFS 都没有，靠"只有 fsync 才保证"绕开。
> LightStore 必须显式选择并写进文档。

## 5. 结论摘要

**建议引入（改造后，去掉服务端阻塞等待）**

1. 卷内空间的乐观大区间租约，竞争时自动收缩（§2.2）
2. 冲突触发式的强保证：单写者零等待，有读者时才同步（§2.3）
3. SDK/客户端缓存按字段变化频率分组，不用 inode 粒度（§2.4）
4. 写缓冲的空间预留策略——至少要显式决策（§2.6）
5. Range 迁移用水位分界 + 读路径双向路由（§2.7）
6. Range 主切换/卷密封/节点下线走主动通知（§2.9）

**可选（取决于目标场景）**

7. 顺序写大文件的 extent 游程压缩，配合批内连续分配（§2.1）
8. 精简版 Glimpse：stat 转发给当前写者，超时回退（§2.5）
9. 去重槽位按操作类别分开（§2.8）

**明确规避**

1. 任何"客户端不响应会阻塞其他客户端"的机制（§3.1）
2. 位置预先确定的公式化布局（§3.2）
3. 延迟同步式的伪冗余（§3.3）
4. 手动分片（§3.4）——但自动分裂要加滞回与限流
