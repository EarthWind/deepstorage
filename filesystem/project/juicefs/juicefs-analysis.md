# JuiceFS 调研（五）：设计评估与启示

> 基线：juicefs v1.5.0-dev，commit `44a5657`

前四篇是事实描述，这一篇是判断。结论分三类：**可借鉴的机制**、**应规避的设计**、**定位决定的取舍（不构成缺陷，但设计新系统时要有意识地做选择）**。

## 1. 定位与评估边界

JuiceFS 的目标是"用最低成本在任意对象存储上得到一个能用的 POSIX 文件系统"。
下面这些结构性选择都是这个目标的直接推论，评估时要先把它们摆在前面：

| 维度 | JuiceFS 的选择 | 直接后果 |
|------|---------------|---------|
| 服务端 | 无（纯客户端 + 第三方元数据引擎 + 对象存储） | 运维成本极低；但所有逻辑跑在客户端，没有地方放"必须持续运行"的任务 |
| 元数据规模上限 | 单引擎实例（Redis 内存 / 单机 SQL / TiKV 集群） | 卷的规模由所选引擎决定，JuiceFS 自身不做分片 |
| 数据存储 | 第三方对象存储，按 block 一对象 | 数据路径极简；小文件与随机读的代价由对象存储承担 |
| 冗余 | 由对象存储负责，JuiceFS 不感知 | 不控制副本放置、修复速度、EC 参数 |
| 小文件 | 一个 slice 至少一个对象，无打包 | 对象数与文件数同量级 |
| 一致性 | 元数据强一致，数据 close-to-open | 无中心协调者下的合理边界 |
| 后台任务 | 客户端抢租约执行 | 依赖至少一个客户端在线 |

JuiceFS 的很多"缺陷"是它定位的必然结果，不构成对它的批评；但如果读者的目标是
自研一套在自有硬件上运行、面向更大规模（数十亿到万亿级文件）的存储系统，这些点恰好标定了必须自己解决的问题边界。

真正值得逐条学习的是**局部机制**——那些与规模无关、纯粹是工程手艺的部分。

## 2. 可借鉴的机制

### 2.1 索引可推导，而非可枚举 ★★★

JuiceFS 最值钱的一个决定：**元数据只存 slice（24 字节），block 的对象 key 由
`(slice_id, block_index, block_size)` 算出来**（[数据路径 1](juicefs-data-path.md#1-三级切分模型)）。
一个 64MiB 的顺序写，元数据成本是 24 字节，对应 16 个对象——而这 16 个对象的名字一个都不用存。

这条原则可以直接抽象为设计约束：

> 任何 per-record 的信息，若能由 (上层 id, 固定参数) 计算得出，就不应落盘。

设计数据索引时可对照检查的点：
- 索引项的 value 是否真的最小？长度、校验等字段若能从数据本身的头部恢复，就不必重复存在索引里。
- 条带 / 分片一类的派生位置，是否可由 `(容器 id, 偏移, 编码参数)` 推导，而不是逐条记录。

代价也要一并接受：**block_size 一旦格式化就不可改**。JuiceFS 在 `Format.update()` 里
硬性拒绝修改这类字段（[总体架构 4](juicefs-overview.md#4-卷volume的概念)）。
采用同类推导的系统，必须明确哪些参数进入"不可变格式"集合，并在配置层拒绝修改。

### 2.2 区间树覆盖展开算法 ★★★

`buildSlice` / `slice.cut`（`pkg/meta/slice.go:55,134`）解决的是任何追加式数据索引都会面对的问题：
**append-only 的覆写序列如何展开成扁平视图**。

覆写有两种实现路径：写入时立即做"区间替换"，需要读改写，会引入并发写冲突；
或者像 JuiceFS 这样追加式记录、后写覆盖先写，把展开推迟到读时。选择后者时，
JuiceFS 的算法可以直接搬：

```
按写入顺序遍历 slice：
  新 slice 在其左边界切树 → 得到 left 子树
  在右边界切剩余部分     → 丢弃中间被完全覆盖的部分
  新 slice 成为根（天然"最新"）
中序遍历，空隙补 id=0 的洞
```

复杂度 O(n log n)，n 是区间数。**关键配套是必须限制 n**——JuiceFS 用三级阈值
（异步 5 / 异步 350 / 同步 2500）做到这一点。任何追加式索引都需要一个
"碎片过多时反压写入"的机制，否则读放大不可控（见 §3.4）。

### 2.3 引用计数"默认 1 即不存在" ★★

`// most of chunk are used by single inode, so use that as the default (1 == not exists)`
（`pkg/meta/redis.go:3144`）。

绝大多数数据块只被一个文件引用，为它们各存一条引用计数记录是纯浪费。
只在 clone / compaction 保留 / 快照等场景写入显式计数。

需要支持 clone / snapshot / 去重的系统，这个技巧直接适用于块级或容器级的引用管理。

### 2.4 属性编码的向后兼容扩展 ★★

`Attr.Unmarshal`（`pkg/meta/interface.go:215`）用 `rb.Left() >= N` 逐段判断可选字段是否存在：

```go
if rb.Left() >= 8  { attr.Parent = Ino(rb.Get64()) }
if rb.Left() >= 8  { attr.AccessACL = rb.Get32(); attr.DefaultACL = rb.Get32() }
if rb.Left() >= 1  { attr.Tier = rb.Get8() } else { attr.Tier = 0 }
```

新版本追加字段，旧客户端读到会自然忽略尾部；旧数据被新客户端读到，缺失字段取零值。
比引入 protobuf 省空间（inode 属性是数量最大的元数据，每字节都乘以文件数），
比纯固定长度灵活。**万亿文件量级下，inode 属性每省 8 字节就是 8TB。**

同时注意它把 `Typ` 和 `Mode` 打包进一个 uint16（`typ<<12 | mode&0xfff`），省 1 字节。
文件数越大，这种级别的抠门越有必要。

### 2.5 预读的双 session + 全局水位反馈 ★★★

`checkReadahead`（`pkg/vfs/reader.go:419`）值得整体移植到任何客户端库：

- **2 个并行 session**：能同时跟踪两条交错的顺序流（典型场景：一个进程同时顺序读两个文件，
  或读写混合）。单 session 的预读器遇到交错访问会直接退化成随机读。
- **倍增/减半**：命中翻倍、失配减半，收敛快且不需要调参。
- **全局缓冲水位参与决策**：`readAheadTotal > used + readahead*4` 才扩大窗口，
  `readAheadTotal < used + readahead/2` 就收缩。多流并发时自动互相退让，
  这是纯单流启发式做不到的。

配套的三层缓冲回收（`cleanupRequests` / `releaseIdleBuffer` / `need()`）同样值得参考，
尤其是 `releaseIdleBuffer` 里"超水位时按超出倍数线性缩短空闲时间"这个自适应细节。

### 2.6 小随机读旁路整块缓存 ★★

`pkg/chunk/cached_store.go:155`：非块首且请求 < 1/4 block 时，直接 range GET，不拉整块。

凡是数据单元较大（MiB 级甚至更大）的系统，小随机读都面临"为读 4KB 拉整块"的风险。
通用做法就是这里的启发式：**以读长度与块长度的比值**决定走整块缓存路径还是精确 range 读。

### 2.7 回收站按小时分目录 ★

`.trash/YYYY-MM-DD-HH/`（`pkg/meta/base.go:3032`），并在客户端本地缓存"当前小时的 trash 目录 inode"，
避免每次删除都查一次。简单有效，直接可用。

### 2.8 slice 提交的依赖链 ★★

`sliceWriter.dep`（`pkg/vfs/writer.go:305`）：新 chunk 的第一个 slice 依赖前一个 chunk 中
最后一个正在扩展长度的 slice，防止文件长度出现"跨过了前面的洞"的中间态。

任何"客户端攒批、异步提交数据索引"的设计都会遇到同一问题：如果按大粒度批量提交，
提交顺序乱了会让其他客户端看到长度已增长但中间区段为空的文件。
**索引提交接口应明确提交顺序约束，或由服务端强制按文件偏移单调提交。**

### 2.9 元数据引擎抽象的分层切法 ★★

`baseMeta`（公共语义）+ `engine`（后端 doXxx）的切分（[元数据 1](juicefs-metadata.md#1-抽象分层)）
把权限检查、配额、缓存、compaction 触发这些**与后端无关的逻辑写了一遍**，
三个后端各 5~6k 行只负责事务内的读写。

即使只有一个自研元数据引擎，也通常会有"底层单机 KV 可替换"（RocksDB / 自研 LSM）
的诉求，这个切法值得参考——尤其是把"什么时候触发 compaction"这类策略放在公共层，
而不是散落在存储引擎里。

## 3. 应规避的设计

### 3.1 后台任务依赖客户端在线 ★★★

`setIfSmall` 抢租约 + 50 分钟自限时（[GC 4](juicefs-gc-consistency.md#4-后台任务的分布式协调)）
是无中心架构下的精巧妥协，但它有个硬前提：**至少一个客户端长期在线**。
全部卸载后，回收站不清理、删除的数据不释放、碎片不合并。

有服务端的系统**不应该复刻这个模式**：修复与 compaction 应由数据服务端（例如数据容器的主副本）驱动，
GC 应由删除日志一类的服务端事件驱动。要确保的原则是：**没有任何后台任务的执行依赖于客户端存在**。

### 3.2 "允许泄漏、事后扫描清理" ★★★

JuiceFS 的多个路径会产生孤儿对象：
- 数据已上传但元数据提交失败（客户端崩溃）
- Compaction CAS 失败，新合并的 slice 无人引用
- 甚至 CAS 成功与否本身可能误判（`pkg/meta/redis.go:3814` 的 double-check）

清理手段是 `juicefs gc`——**全量扫描对象存储，比对元数据引用**。
在 PB 级卷上这已经是数小时的操作；到 EiB 级、万亿记录规模，
**全量扫描在物理上不可行**。

设计新系统时应把"没有任何组件需要遍历全部文件/记录"落实为具体机制，一种可行的思路：

- 让写入失败不产生孤儿：数据在容器内追加写入时携带反向指针（`owner = (inode, file_offset)`），
  未被索引引用的记录在容器局部的 compaction 时即可识别为死数据。
  回收是容器局部的，不需要全局扫描，比全量比对好一个数量级。
- 但要确认：**反向指针校验必须能独立判定"这条记录是否还被引用"**，
  即 compaction 时对每条记录反查索引。这是容器粒度的 O(容器内记录数) 操作，
  可接受；要避免退化成全局 join。

### 3.3 小文件无打包 ★★★

JuiceFS 每个 slice 至少产生一个对象。100 亿个 4KB 小文件 = 100 亿个对象。
对象存储的 LIST/DELETE 成本、per-object 元数据开销、以及 4KB 对象的 IO 效率都很差。

面向海量小文件的系统通常选择 Haystack 式打包，方向明确正确。但要注意配套问题：

- **打包后的删除更难**：JuiceFS 删一个小文件就是删一个对象；打包之后删一个小文件
  只是在容器里留一个洞，必须靠 compaction 回收。compaction 的触发阈值
  （死数据占比）需要仔细设计，否则要么空间浪费、要么 compaction 打满 IO。
  可以参考 JuiceFS 的 `skipSome` 思路（[GC 1.3](juicefs-gc-consistency.md#13-skipsome不重复搬运大块)）：
  **只搬运碎片，跳过仍然连续且足够大的区段**。

### 3.4 碎片上界只靠客户端自觉 ★★

JuiceFS 用 `maxSlices = 2500` 同步阻塞写入来兜底（[GC 1.1](juicefs-gc-consistency.md#11-触发)），
这条防线本身是对的；问题在于它由客户端执行——一个跳过该检查的旧版或有 bug 的客户端
就能把 chunk 写碎到读放大失控，元数据引擎不会拒绝。

采用追加式索引的系统需要一个等价机制，且最好放在服务端：**由元数据服务统计单文件
（或单分片内单 inode）的索引条数，超阈值时对写入返回软反压信号，由客户端触发同步 compaction。**

### 3.5 客户端版本管理 ★★

JuiceFS 把全部逻辑放在客户端，导致：
- 升级 = 让所有挂载点重新挂载
- 新老版本客户端同时访问同一个卷，靠 `Format.MinClientVersion` / `MaxClientVersion` 做兼容性守卫
- 一个有 bug 的客户端可以破坏卷（比如错误的 compaction CAS）

有服务端的系统可以把 compaction、修复、GC 这类"能破坏数据"的操作**完全收在服务端**，
客户端只做 IO。这是架构优势，应该明确利用——**不要为了性能把 compaction 下放到客户端库**。

### 3.6 元数据引擎无分片层 ★★★

这是 JuiceFS 最大的规模瓶颈：单卷元数据必须放进一个引擎实例。
Redis 受内存限制（亿级文件已经吃力），SQL 受单机限制，TiKV 能扩展但每个操作变成分布式事务。

在元数据分片之外，调研中值得注意的一个细节是
JuiceFS 的 **TKV key 布局把一个 inode 的所有元数据挂在 `A{inode}` 前缀下**
（[元数据 3.1](juicefs-metadata.md#31-tkvtikv--etcd--badgerdb--foundationdb--memkv)）：
属性、dentry、chunk、xattr 全部物理相邻。

好处：删除一个 inode = 删一个前缀；dump/clone 一次 range scan 拿全。
坏处：**同一目录下的子项不相邻**——dentry 挂在 parent 前缀下、inode 数据挂在自己前缀下，
`readdir plus` 仍需 N 次点查。

另一种布局是"key 编码保证目录局部性：一个目录的全部 dentry 在 key 空间连续"，
对 `readdir` 友好、对超大目录跨分片友好，更适合万亿级规模。
但要注意 JuiceFS 换来的好处会随之失去：**删除一个 inode 需要多次跨分片的操作**，
inode 属性、数据索引、dentry 可能落在不同分片，这条路径的事务边界必须明确设计。

## 4. 定位决定的取舍

下面几点在 JuiceFS 的架构下是合理选择，不能算缺陷；但有服务端的系统可以做出不同选择，
设计时应有意识地评估代价。

| 点 | JuiceFS | 说明 |
|----|---------|------|
| 冗余 | 完全外包给对象存储 | 简化了系统，但也失去了对副本放置、修复速度、EC 参数的控制权。自管冗余的动机通常是修复速度与成本（EC 可到 1.33x 左右） |
| 一致性 | close-to-open | 无中心协调者下的合理选择。有元数据服务端的系统可以做更强的语义，但要评估代价 |
| 锁 | 非阻塞，EAGAIN + 上层轮询 | 因为没有地方挂等待队列。有元数据服务端就可以实现真正的阻塞锁 |
| 配额 | 弱一致，允许短暂超配 | 同上，无协调者的必然结果。要精确配额，需要评估每次写入做一致性读的代价——大概率仍应选择弱一致 + 定期纠偏 |

第四条要特别提醒：**有服务端不等于配额就能强一致**。
在千万 ops/s 量级的目标下，每次写入同步更新目录配额会让配额所在的分片成为热点。
JuiceFS 的做法（本地累积 delta + 秒级 flush + 定期重载纠偏，
[元数据 8](juicefs-metadata.md#8-quota)）在这里仍然是正确答案。

## 5. 结论摘要

**值得直接借鉴的机制**

1. 索引可推导原则——per-record 信息若可计算则不落盘（§2.1）
2. 区间树覆写展开算法 + 碎片数量的三级反压阈值（§2.2、§3.4）
3. 预读的双 session + 全局缓冲水位反馈（§2.5）
4. 属性编码的紧凑二进制 + 尾部可选字段兼容（§2.4）
5. 索引批量提交的顺序约束，防止文件长度中间态（§2.8）
6. 配额走弱一致 + 定期纠偏，而非强一致（§4）

**应规避的设计**

1. 后台任务依赖客户端在线（§3.1）
2. 依赖全量扫描的 GC——EiB 级不可行，应靠容器局部反向指针回收（§3.2）
3. 把 compaction 等破坏性操作放在客户端（§3.5）
4. 单卷元数据无分片层（§3.6）
5. 海量小文件不打包（§3.3）

**JuiceFS 反向印证的规模化方向**

1. 元数据分片，突破单引擎瓶颈（§3.6）
2. 小文件打包进容器（§3.3）
3. 后台任务由服务端驱动（§3.1）

**规模化设计中需要补充解决的问题**

1. 单文件索引条数的上界保护与服务端反压机制（§3.4）
2. 目录局部性布局下跨分片删除 inode 的事务边界（§3.6）
3. 打包容器 compaction 的触发阈值与"只搬碎片"策略（§3.3）
4. 小随机读旁路整块读取的启发式（§2.6）
